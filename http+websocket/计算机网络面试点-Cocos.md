# 计算机网络面试点（14k · Cocos Creator 游戏开发）

> 面向客户端 / 小游戏 / H5 游戏岗：重点吃透 **HTTP/1 · HTTP/2 · HTTP/3** 与 **长连接**，并能落到资源加载、CDN、WebSocket、帧同步/状态同步等场景。

---

## 一、先建立面试叙事（一句话版本）

| 协议 | 一句话 |
|------|--------|
| HTTP/1.1 | 文本协议 + 短连接默认改成长连接；同域并发受浏览器连接数限制，易队头阻塞 |
| HTTP/2 | 二进制多路复用；一个 TCP 连接上并行多请求；头部压缩；仍受 TCP 队头阻塞 |
| HTTP/3 | 基于 QUIC（UDP）；流级独立，丢包不堵整连接；自带 TLS；更适合弱网/移动端 |
| 长连接 | 少握手、少延迟；游戏里常指 Keep-Alive / WebSocket / 自研 TCP/UDP 长链 |

面试官常追问：**「你们项目资源怎么加载？为什么用/不用 HTTP2？实时玩法用什么连接？」** —— 答完协议对比后，一定落到 Cocos / 小游戏场景。

---

## 二、必备地基（被追问时用）

### 2.1 OSI / TCP·IP 与游戏相关层

- **应用层**：HTTP、WebSocket、自定义协议  
- **传输层**：TCP（可靠、有序）/ UDP（快、不可靠）/ QUIC（UDP 上做可靠）  
- **网络层**：IP、路由、NAT  

### 2.2 TCP vs UDP（游戏必考）

| | TCP | UDP |
|--|-----|-----|
| 可靠性 | 有（重传、确认） | 无（应用层自己保证） |
| 顺序 | 保证 | 不保证 |
| 延迟 | 丢包时整连接可能卡住 | 可只丢一包 |
| 典型用途 | 登录、支付、HTTP、可靠指令 | 实时位置、语音、帧同步广播 |
| 游戏选型 | 状态同步里的可靠通道、大厅 | 战斗实时、弱网优化方案 |

**常问**：帧同步为何偏 UDP？状态同步为何常 TCP/WebSocket？答案：实时性 vs 一致性权衡。

### 2.3 三次握手 / 四次挥手（记结论即可）

- 握手目的：确认双方收发能力，协商初始序号  
- 挥手为何四次：半关闭，一方先不发还可以收  
- **TIME_WAIT**：主动关闭方等待，防旧包干扰新连接  
- 与 HTTP 关系：每次新建 TCP 都有 RTT 成本 → 催生长连接、连接复用

### 2.4 TLS / HTTPS（HTTP2/3 绕不开）

- 握手额外 RTT（TLS1.3 可 1-RTT，甚至 0-RTT）  
- HTTP/2 在浏览器里几乎强制 HTTPS  
- HTTP/3：QUIC 内置加密，握手与连接建立更合并  
- 证书、SNI、中间人：CDN / 热更域名配置相关

## 三、HTTP/1.x（必须讲清「痛点」）

### 3.1 核心特征

- 请求-响应模型；明文文本（除 HTTPS）  
- HTTP/1.0：默认短连接，每次请求新建 TCP  
- HTTP/1.1：默认 **Keep-Alive**（长连接）；支持 `Host`、分块传输 `Transfer-Encoding: chunked`  
- **队头阻塞（HOL Blocking）**：同一条 TCP 上请求串行排队，前一个慢后面全堵  
- 浏览器同域并发连接数约 **6**（历史限制）→ 催生域名分片（domain sharding）

### 3.2 优化手段（面试常考「老项目怎么优化」）

| 手段 | 原理 | 副作用 |
|------|------|--------|
| Keep-Alive | 复用 TCP，少握手 | 连接占用；空闲超时 |
| 管道化 Pipelining | 连续发多个请求 | 实现差、基本被弃用 |
| 雪碧图 / 合并请求 | 减少请求数 | 缓存粒度变差 |
| 资源压缩 / CDN | 减体积、近源 | 配置成本 |
| 域名分片 | 绕过 6 连接限制 | HTTP/2 下反而不利（见下） |

### 3.3 Cocos / 游戏资源场景话术

- 首包大量小图、配置 JSON、音频：HTTP/1 下「请求多 + 连接数限制」会明显拖慢加载  
- 热更清单、分包下载：注意 Keep-Alive 与 CDN 超时  
- 小游戏环境：宿主对并发、域名、HTTPS 有额外限制，不能假设和浏览器一致

---

## 四、HTTP/2（面试高频对比点）

### 4.1 相对 HTTP/1 的关键升级

1. **二进制分帧**：Frame → Stream → Message，不再纯文本行解析  
2. **多路复用（Multiplexing）**：单连接上多路流并行，基本解决 HTTP 层队头阻塞  
3. **头部压缩 HPACK**：重复 Header（Cookie、UA）大幅减小  
4. **服务端推送 Server Push**：可主动推资源（实际落地有限，很多场景不用）  
5. **流优先级 / 依赖**：可表达资源重要程度（实现参差）

### 4.2 仍未解决的问题

- **TCP 队头阻塞**：一个包丢失，TCP 滑动窗口内后续数据卡住 → 所有 Stream 受影响  
- 弱网、移动网络切换时，TCP 表现差  
- 单连接拥塞控制：偶发丢包可能拖慢整页/整批资源

### 4.3 实践注意（容易加分）

- HTTP/2 下 **不要再域名分片**，应合并到更少连接，发挥多路复用  
- 仍建议合理拆包、缓存、CDN；协议不能替代资源策略  
- 浏览器：h2 基本必须 TLS  
- ALPN 协商：ClientHello 里协商 h2 / http/1.1  

### 4.4 游戏向问答示例

> Q：Cocos 远程加载大量 texture，HTTP/2 有什么好处？  
> A：少连接、多请求并行、头部开销小，首屏/热更并发加载更稳；但弱网丢包时仍可能整连接变慢，这时可看 HTTP/3 或分域名容灾。

---

## 五、HTTP/3（差异化加分项）

### 5.1 核心：HTTP over QUIC

- 传输从 TCP 换成 **QUIC（基于 UDP）**  
- 应用语义仍是 HTTP（方法、状态码、Header 等）  
- 加密内置（大致等价 TLS1.3）  
- 连接用 **Connection ID** 标识，IP/端口变化可迁移（移动切 WiFi/4G 友好）

### 5.2 相对 HTTP/2 的关键收益

| 点 | HTTP/2 (TCP) | HTTP/3 (QUIC) |
|----|--------------|---------------|
| 丢包影响 | 可能堵整连接 | 主要影响单个 Stream |
| 握手 | TCP + TLS 多 RTT | 常可 1-RTT，甚至 0-RTT 复用 |
| 连接迁移 | IP 变通常要重连 | Connection ID 可迁移 |
| 中间设备 | TCP 兼容好 | 部分网络 UDP/QUIC 被墙或限速 |

### 5.3 风险与落地

- 企业网、运营商可能干扰 UDP → 需 **回落 h2/h1**  
- 服务端 / CDN 要开启 h3（Cloudflare、部分云厂商已支持）  
- 小游戏、原生壳、部分 WebView 对 h3 支持不一致 → 面试说「看运行时与 CDN 能力」更稳妥

### 5.4 一句话对比（背这个）

> HTTP/1 解决「能不能传」；HTTP/2 解决「一条连接上并发传」；HTTP/3 解决「弱网丢包别拖死整条连接」。

## 六、长连接（本岗位核心）

### 6.1 「长连接」到底指什么（别混）

| 类型 | 含义 | 游戏场景 |
|------|------|----------|
| HTTP Keep-Alive | 同一 TCP 上多次 HTTP 请求 | 资源加载、短 API |
| HTTP/2 单连接多路复用 | 长生命周期 TCP + 多 Stream | CDN 静态资源 |
| WebSocket | 全双工长连接，帧协议 | 大厅、聊天、匹配、部分状态同步 |
| TCP/UDP 自定义长链 | 自研包头 + 心跳 | 强联网对战、帧同步 |
| SSE | 服务端单向推流 | 少用于强交互游戏 |

### 6.2 HTTP Keep-Alive 要点

- `Connection: keep-alive`（1.1 默认）  
- 服务端/代理有 **空闲超时**；超时后客户端需重连  
- 好处：摊薄握手与慢启动成本  
- 坏处：占 FD、占内存；短连接突发下也可能不划算  
- 与「真正的实时通道」不同：仍是请求-响应，服务端不能任意推（除非挂起长轮询）

### 6.3 短轮询 / 长轮询 / WebSocket

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| 短轮询 | 定时请求 | 简单；空耗流量与连接 |
| 长轮询 | 服务端挂起至有数据或超时 | 比短轮询实时；仍偏 HTTP 语义 |
| WebSocket | 一次 Upgrade，之后双向帧 | 实时好；要心跳、重连、鉴权 |

**握手路径**：HTTP `Upgrade: websocket` → 101 Switching Protocols → 之后不再是普通 HTTP 请求模型。

### 6.4 游戏长连接必谈：心跳、重连、粘包

1. **心跳（Heartbeat）**  
   - 检测死连接、过 NAT、保活  
   - 间隔过大：发现断线慢；过小：费电费流量  

2. **断线重连**  
   - 指数退避、最大次数、登录态/房间态恢复  
   - 区分「网络瞬断」与「被踢 / Token 失效」  

3. **粘包 / 半包（TCP）**  
   - TCP 是字节流：需长度头、分隔符或固定长度  
   - UDP 是报文：一般无粘包，但有丢包乱序  

4. **序列号 / ACK**  
   - 可靠业务（进出房、结算）要应用层确认  
   - 实时位置可「只发最新」丢弃过期  

5. **协议设计**  
   - 包头：长度、消息号、序列号、压缩标志  
   - 可选 protobuf / JSON；注意加密与防篡改  

### 6.5 Cocos Creator 侧常见考点

- `WebSocket` / 原生 socket 插件 / 小游戏 `wx.connectSocket` 等差异  
- 切后台：连接被杀、心跳暂停、恢复后重连与状态校准  
- HTTPS / WSS：上线域名与证书；明文 WS 常被禁  
- 资源用 HTTP(S)，实时逻辑用 WS/TCP —— **通道分离** 是稳妥架构话术  
- 弱网：超时、队列积压、本地预测与和解（状态同步）

## 七、横向对比速查表（面试临场用）

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|--------|--------|
| 传输 | TCP | TCP | QUIC(UDP) |
| 多路复用 | 弱（易队头堵） | 有（HTTP 层） | 有（流更独立） |
| 头部 | 明文重复 | HPACK | QPACK |
| 队头阻塞 | HTTP + TCP | 主要剩 TCP | 大幅缓解 |
| 浏览器连接策略 | 多连接 / 分片 | 少连接更好 | 少连接 |
| 加密 | 可选（现多强制） | 基本强制 TLS | 内置 |
| 连接迁移 | 差 | 差 | 好 |
| 典型游戏用途 | 兼容、简单 API | 资源 CDN 主流 | 弱网资源加速（逐渐普及） |

| 长连接形态 | 是否全双工 | 是否适合战斗实时 | 备注 |
|------------|------------|------------------|------|
| HTTP Keep-Alive | 否 | 否 | 适合资源/REST |
| 长轮询 | 近似 | 较差 | 过渡方案 |
| WebSocket | 是 | 中高（看帧率与架构） | H5/小游戏常见 |
| TCP 自定义 | 是 | 高（可靠需求） | 注意粘包心跳 |
| UDP/KCP/自研 | 可设计 | 很高 | 帧同步常见 |

## 八、CDN / 缓存 / 跨域（资源加载连带问）

### 8.1 缓存相关头

- `Cache-Control` / `ETag` / `Last-Modified`  
- 热更：版本号或 hash 文件名 → **永不缓存入口清单，长缓存带 hash 资源**  

### 8.2 CDN

- 就近节点、回源、缓存击穿  
- HTTPS 证书、HTTP/2/3 是否开启看 CDN 配置  
- 防盗链、Referer、鉴权 URL（有效期）  

### 8.3 CORS

- 浏览器同源策略；`Access-Control-Allow-Origin`  
- 预检 OPTIONS；游戏里远程加载纹理/音频也可能踩 CORS  
- Cocos 远程资源、第三方存储桶要配 CORS

## 九、高频面试题（建议口述答案）

### A. 协议对比类

1. HTTP/1.1 与 HTTP/2 最大区别？ → 二进制、多路复用、HPACK；仍基于 TCP。  
2. HTTP/2 为何还有队头阻塞？ → TCP 可靠有序，丢包堵后续。  
3. HTTP/3 解决了什么？ → QUIC 流独立 + 更好的握手与连接迁移。  
4. 为什么 HTTP/2 不建议域名分片？ → 破坏单连接多路复用与拥塞估计。  

### B. 长连接类

5. Keep-Alive 和 WebSocket 区别？ → 前者仍是请求响应复用 TCP；后者是持久全双工帧通道。  
6. 如何判断长连接断开？ → 心跳超时、TCP 错误回调、应用层超时。  
7. TCP 粘包怎么处理？ → 长度前缀为主；再谈半包缓冲拼接。  
8. 游戏为何要心跳？ → NAT/防火墙、检测假死、保活。  

### C. 游戏落地类

9. 资源加载用啥，实时战斗用啥？ → HTTPS（最好 h2/h3）加载；WS/TCP/UDP 实时。  
10. 弱网怎么优化？ → 协议选型、重传策略、预测和解、降频、超时与重连、CDN。  
11. 小游戏环境注意什么？ → 域名白名单、WSS、并发限制、后台杀连接。  
12. 帧同步 vs 状态同步对网络的要求？ → 帧同步敏感延迟与丢包补偿；状态同步敏感带宽与一致性。  

### D. 易错概念

13. HTTP 是无状态的，那 Cookie/Session/Token 是什么？ → 协议无状态；应用用头/存储维持会话。  
14. HTTPS 一定比 HTTP 慢吗？ → 握手有成本；长连接 + TLS1.3/会话恢复后差距很小，安全收益更大。  
15. QUIC 是 UDP 所以不可靠？ → 否，QUIC 在 UDP 上实现了可靠、拥塞控制等。

## 十、结合 Cocos Creator 的「项目故事」模板

面试时用这个结构讲你做过的项目（按需填空）：

1. **资源**：远程 Asset Bundle / 热更走 HTTPS，CDN 开 HTTP/2；清单短缓存，hash 资源长缓存。  
2. **大厅**：WebSocket（WSS）长连接，心跳 15–30s，断线指数退避重连，Token 续期。  
3. **战斗**：状态同步走 WS/TCP；或帧同步走 UDP/KCP；关键指令应用层可靠。  
4. **弱网**：超时提示、本地预测、关键操作排队、重连后状态快照对齐。  
5. **踩坑**：后台切回连接失效、粘包未处理导致乱指令、HTTP/1 下小图过多加载慢、域名分片在 h2 负优化。
